# sanitise-diff

## When to use

- Before claiming ready to commit / open a PR.
- After `git add`.
- User asks to sanitise or scrub the diff.

## Procedure

1. Inspect **staged** diff; **added** lines only (`+`), exclude `data/` (gitignored
   reference is fine there):

```bash
git diff --cached -- ':!data/'
```

2. Repo policy (full text: `data/changes/CONVENTIONS.md` / `CLAUDE.md`):

```bash
# client names (extend alternation as needed — see CONVENTIONS.md)
git diff --cached -- ':!data/' | grep -Ei "$(cat .sanitise-names)"   # one name per line, ALTERNATION-joined; see note below \
  && echo "BLOCKED: client name" || echo "OK names"

# ticket IDs in added body lines (filenames test_sst_NNNN_*.py OK)
git diff --cached -- ':!data/' ':!CLAUDE.md' ':!AGENTS.md' | grep -E "^\+.*\b(SST|PV)-[0-9]+" \
  && echo "BLOCKED: ticket ID in body" || echo "OK tickets"
```

Also flag: secrets/tokens, signed URLs with credentials, and agent attribution
(“Generated by…”, “Co-Authored-By: Cursor/Claude”, etc.) in committed artifacts.

3. Fix or unstage; re-run until clean. Never skip because “this one looks clean.”

## Output format

```text
Sanitise report
- Staged files: …
- Added-line scan: CLEAN | HITS
- Hits: <file:reason> …
- Actions taken: …
- Ready for human gate: yes/no
```

## ⚠️ Where the name list lives

The blocklist itself is **client data**. Keeping it inline means the file whose job is to catch
client names is the one file guaranteed to contain all of them — and that file gets copied into
examples, pasted into tickets and shipped in onboarding packs. (That is exactly what happened when
this skill was first extracted for teaching: the sanitiser was the only leak.)

Keep the names in a **gitignored** side file (`.sanitise-names`, one regex-safe name per line) and
have the skill read it. The skill is then publishable; the list never leaves the machine.

```bash
# .gitignore
.sanitise-names
```

Same reasoning as every other per-machine file in this methodology: the *mechanism* is shared, the
*content* is not.
